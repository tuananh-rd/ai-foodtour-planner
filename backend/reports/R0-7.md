## Defensive cache review (findings only)

1. Remaining module-global private-text path: `backend/app/planner/relevance.py`
   `_phrases(interest)` calls `fold(interest)`, whose `@lru_cache(maxsize=8192)`
   retains original strings as keys without TTL. `interest_score` and `excluded`
   feed it user-controlled preference interests/exclusions. Structured requests
   or LLM-extracted terms can therefore retain private snippets, including a
   whole short chat message if extracted as a term (`provider._terms` permits
   arbitrary strings up to 40 characters). The direct raw chat normalization
   in extract/provider correctly uses `fold_uncached` after `324a651`.
   Minimal synthetic reproduction in an isolated Python process:

   ```text
   fold.cache_clear()
   before: CacheInfo(hits=0, misses=0, maxsize=8192, currsize=0)
   _phrases('synthetic private chat phrase')
   after: CacheInfo(hits=0, misses=1, maxsize=8192, currsize=1)
   ```

2. `RulesFirstExtractor._cache` is application-instance shared (not a module-global
   LRU), keyed by SHA-256 of normalized chat plus prior preferences. Successful
   `ExtractionResult` values still contain private derived preferences and
   `origin_text`; storage is bounded to 256 with a default 3600-second logical
   TTL. Expiration is lazy: stale entries are removed on matching reads or a
   subsequent successful LLM insertion, so idle instances can retain objects
   beyond that TTL. Hashing the key does not anonymize stored result values.

3. CheckedExplainer caches checked tour facts/results rather than raw chat;
   venue repository and routing caches do not accept chat. No additional direct
   raw-chat global memoization site was found in backend/app searches.

No cache code changed, per the report-only scope. Claude should decide the
follow-up for uncached user terms and private extraction-result retention.
